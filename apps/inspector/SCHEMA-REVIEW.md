# Schema-by-schema review

Reviewed all 184 detector registrations and the additional DLL sample. **110 registrations expanded**, sharing implementations where their outer container is identical. The other 74 keep their existing layout; the table records the reason and useful future candidates. Retained does not mean further parsing is impossible.

Expansions live in [schema-expansions.ts](src/schema-expansions.ts), applied by [schemaForFile](src/detected-schemas.ts) during detection or when loading an unedited schema template. Each generated schema describes its actual coverage. The nine sample-backed demonstrations remain synchronized with their managed-library fixtures: their deliberately small sample bytes cannot demonstrate later records. Use **Load & detect** on a real file for the expanded layout.

## Language review

The layouts demonstrate enums, low-bit-first bitfields (including 64-bit FLAC fields), nested structures, runtime-length arrays, multidimensional float arrays, signed values, explicit byte order and typed 32/64-bit pointers. Native `if`/`switch` groups handle per-record variants in ZIP, PE, CRX, DICOM, LZ4, Zstandard, PNG, RIFF, movie headers and GLB. The schemas also use 24-bit integers, bounded text encodings, LEB128, fixed-point values and explicit GUID storage. Preview scanning still chooses bounded record counts and additional format-specific expansions. Generic loops, decompression and full container decoding remain outside these layouts.

Scans use at most the first 64 KiB, with 16 ZIP/FLAC records, 32 chunks/packets/sections or 128 ELF table entries/STL triangles. Typed pointers may read beyond that preview from the full loaded file. A zero-size ISO box means actual EOF, so only its header is exposed. Compressed/encrypted bodies stay opaque. These are inspection layouts, not validators or complete decoders. Reload detection after changing format-defining bytes.

## Text-field audit

Reviewed array declarations in all 184 detector profiles, file-selected expansions, and the nine sample schemas. The samples already use character arrays for names and labels. Corrections preserve the original storage extent:

| Fields                     | Representation                                                                                                                   |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| ZIP-family entry filenames | Per-entry `utf8[length]` when bit 11 is set, otherwise `cp437[length]`; EOCD comments remain raw `char`                          |
| Binary CPIO entry name     | `char[name_size]`, retaining the counted NUL terminator                                                                          |
| ASAR JSON directory        | `utf8[json_length]`; the count remains encoded bytes                                                                             |
| Registry hive filename     | `wchar< file_name_utf16le[32]`, preserving the 64-byte UTF-16LE buffer                                                           |
| PNG/APNG `tEXt` chunk      | `latin1 text[length]`, preserving the keyword separator and Latin-1 text                                                         |
| DICOM first-element value  | `char[value_length]` for text VRs; numeric VRs use typed arrays when divisible by their storage width; other values remain bytes |

Retained byte arrays include binary signatures, digests, packed bitstreams, padding, compressed/encrypted data, ZIP extra records, mixed binary/text metadata blocks, and generic payloads. STL's 80-byte header need not be text. XML prefixes retain bytes because the encoding can vary. PNG compressed text stays opaque; well-framed uncompressed `iTXt` exposes Latin-1 keywords and bounded UTF-8 translated keywords/text.

`char` means raw U+0000–U+00FF code units, not a UTF-8 decoder. Fixed character arrays retain embedded NULs and do not search beyond a counted field for a terminator. DICOM non-default character sets are not automatically transcoded. ZIP legacy names use CP437; Unicode extra-field overrides and producer-specific legacy code pages remain unsupported. See [character-buffer semantics](../../docs/language/arrays-and-strings.md).

References: [ZIP encoding flags](https://pkware.cachefly.net/webdocs/casestudies/APPNOTE.TXT), [ASAR format](https://github.com/electron/asar/blob/main/README.md), [CPIO pathname storage](https://commons.apache.org/proper/commons-compress/apidocs/org/apache/commons/compress/archivers/cpio/CpioArchiveEntry.html), [DICOM VRs](https://dicom.nema.org/medical/dicom/current/output/chtml/part05/sect_6.2.html), [PNG text](https://www.w3.org/TR/png-3/), and [registry-hive layout research](https://projectzero.google/2024/12/the-windows-registry-adventure-5-regf.html).

## Verification

Every registration is compiled by the real WASM runtime. Value-level browser tests cover FLAC bitfields, ZIP flags/payload, ELF pointer tables, STL floats/vertices, GLB JSON, PNG chunks, RIFF chunks, OpenType head pointers, WebAssembly sections and Zstandard descriptor widths. The optional upstream audit records read errors separately from schema compilation errors; detector fixtures can be truncated.

## Three-byte integer migration

FLAC metadata lengths and STREAMINFO frame sizes now use `uint24>`; WebP VP8X
canvas dimensions use `uint24<` and retain their stored minus-one values.
Zstandard exposes its first packed block header as `uint24<`: bit 0 is last-block,
bits 1–2 are block type, and bits 3–23 are block size. It is not a 24-bit bitfield
because the library deliberately rejects that storage type for bitfields.
VOC inspects one complete, nonzero-length block after its declared header, or a
one-byte terminator. Zero-length-to-EOF extensions and audio decoding remain
unsupported. Reserved bytes, RGB triples and opaque three-byte identifiers stay arrays.

Sources: [FLAC RFC 9639](https://www.rfc-editor.org/rfc/rfc9639.html),
[WebP container specification](https://developers.google.com/speed/webp/docs/riff_container),
[Zstandard format](https://github.com/facebook/zstd/blob/dev/doc/zstd_compression_format.md),
and [FFmpeg VOC reader](https://github.com/FFmpeg/FFmpeg/blob/master/libavformat/voc_packet.c).

## Encoded metadata and identifier migrations

ASAR and GLB JSON decode byte-bounded UTF-8. PNG tEXt uses Latin-1; complete
uncompressed iTXt exposes its keyword, language tag, translated keyword and text.
Compressed or malformed iTXt stays opaque.

OpenType head revision and ICC illuminant XYZ use signed 16.16. Checksums and
profile digests keep their integer/byte representations. Sources:
[OpenType head](https://learn.microsoft.com/en-us/typography/opentype/otspec190/head)
and [ICC profile format](https://www.color.org/icc1-v41.pdf).

ASF object IDs, Shell Link/compound-file class IDs, CHM header GUIDs and WAVE
extensible SubFormat use Windows `guid` storage. Hashes, universal labels and
opaque signatures remain bytes. Sources:
[Shell Link](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-shllink/747629b3-b5be-452a-8101-b9a2ec49978c),
[WAVEFORMATEXTENSIBLE](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ksmedia/ns-ksmedia-waveformatextensible).

WebAssembly section lengths use runtime `uleb128_32`; preview scanning still
bounds section counts. Instruction bodies remain opaque. Canonical writing can
change padded lengths; in-place updates reject changes to encoded width.

ZIP local entries select `filename_utf8` or `filename_cp437` from each entry's
UTF-8 flag using native conditional fields. Mixed encodings within one archive
are supported. CP437 is the legacy default; Unicode-path extra-field overrides
are not yet applied, and producer-specific legacy encodings may differ.

DICOM explicit-VR framing follows the [Part 5 short-VR allowlist](https://dicom.nema.org/medical/dicom/current/output/chtml/part05/chapter_7.html#sect_7.1.2): every other VR, including `SV`, `UV` and unknown codes, uses reserved bytes followed by a 32-bit byte length. Browser fixtures assert numeric values and exact eight-byte ranges for `SV`/`UV`, and opaque bytes for an unknown VR. Undefined-length item sequences and dataset transfer-syntax decoding remain unsupported.

### RIFF native record dispatch

RIFF chunk FourCCs are now `riff_kind` enums backed by little-endian `uint32` values, so native `switch` groups select named WAVE, AVI or WebP records. Unknown tags and undersized metadata remain bounded byte arrays. JavaScript only scans complete chunk extents (up to 32 within the preview); it no longer chooses each chunk's payload layout. Chunk padding is preserved independently of the payload length.

WAVE `fmt ` records use the runtime format tag, chunk length and extension size to select extensible metadata. The GUID is decoded only when the extension declares at least 22 bytes and fits inside the chunk; otherwise extension bytes remain opaque. The same generated schema is tested against extensible, PCM, invalid-extension and unknown-tag inputs, including exact GUID debug spans, unknown payloads, nonzero padding and byte-for-byte serialization.

Sources: [Microsoft RIFF framing](https://learn.microsoft.com/en-us/windows/win32/xaudio2/resource-interchange-file-format--riff-), [WAVEFORMATEXTENSIBLE](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ksmedia/ns-ksmedia-waveformatextensible), and [WebP container metadata](https://developers.google.com/speed/webp/docs/riff_container).

### PNG native metadata variants

PNG/APNG chunk tags use big-endian `uint32` enum values to drive native switches. Length-checked named variants expose gamma, physical resolution, animation/frame control, timestamps and rendering intent. Palettes use arrays of RGB structs only when the length is divisible by three; invalid metadata sizes and unknown/image chunks remain bounded bytes. Gamma retains its decimal scale of 100000; it is not a binary fixed-point value.

`tEXt` remains a bounded Latin-1 string including the keyword separator. `iTXt` still uses a bounded preview scan to locate keyword/language/translation separators; reload detection if these positions change. Within this framing, native conditions decode uncompressed text as bounded UTF-8 or preserve compressed text as bytes, based on the runtime compression flag/method. No decompression or CRC validation is performed.

Browser tests reuse a generated schema across metadata tags, lengths, palettes, text, opaque image payloads and international-text compression flags. They assert exact serialization and metadata debug spans. Source: [W3C PNG specification](https://www.w3.org/TR/png-3/).

### WebAssembly variable-integer metadata

The inspector reads section lengths, vector counts, function type-index arrays (up to 1024 entries), start-function indexes and data-segment counts as `uleb128_32`. Custom sections expose byte-bounded UTF-8 names and retain their remaining data. Other section contents, including instruction bodies, stay opaque after their count. The preview scanner validates every expanded integer within its section and keeps malformed metadata opaque; it does not validate module ordering or references.

Section payloads are not independent bounded reader substreams. The generated schema retains preview-derived integer widths for opaque remainders; regenerate it after structural edits. Padded LEB128 values are readable, but serialization canonicalizes them and does not automatically repair enclosing section sizes. Editing such files requires rebuilding those sizes as well.

Source: [WebAssembly binary modules](https://webassembly.github.io/spec/core/binary/modules.html). Browser fixtures cover multi-byte indexes, counts, a non-ASCII custom name, exact index debug spans and canonical byte-for-byte serialization.

### Ogg comment text

Vorbis and Opus vendor strings and user comments now use length-bounded `utf8` fields when a complete comment packet begins on the second physical page, belongs to the same stream serial number and fits in the preview. Up to 128 comments are expanded after validating all string lengths against the packet boundary. Vorbis's framing byte and Opus's optional trailing bytes are preserved. Continued packets, interleaved streams, oversized metadata and packets spanning pages remain unexpanded; no page CRC checks or packet reconstruction are performed. Preview-derived page offsets and trailing extents require detection to be refreshed after structural edits.

Opus output gain remains `int16 output_gain_q8`: its signed 8-fraction-bit representation is not interchangeable with unsigned `ufixed8_8`, and this plan does not add a signed 16-bit fixed-point codec. Codec signatures remain `char` byte code units.

Sources: [Vorbis comment specification](https://xiph.org/vorbis/doc/v-comment.html) and [Ogg Opus RFC 7845](https://www.rfc-editor.org/rfc/rfc7845.html). Browser tests cover both codecs with non-ASCII vendor/comment values, exact byte spans and serialization; preview checks reject continued packets, different stream serials and oversized vendor lengths.

### Movie-header fixed-point metadata

Bounded `moov` containers now expose up to 32 immediate children, decoding `mvhd` version 0/1 time fields, preferred rate and the display matrix. Native version branches retain unknown or undersized headers as bytes. `fixed16_16` stores the preferred rate and the first two values of each matrix row; `fixed2_30` stores the perspective column, in on-disk order a,b,u,c,d,v,x,y,w. The six words after the matrix retain a format-neutral name because QuickTime time fields and ISO reserved fields share this position.

`preferred_volume_q8` remains signed `int16` storage: an unsigned 8.8 codec would change the domain. Child track/codec contents remain opaque. Extended-size or zero-size child boxes stop expansion and preserve the remaining container bytes. The preview determines child coverage; regenerate after structural edits. No media decoding or movie validity checks are performed.

Sources: [Apple movie header](https://developer.apple.com/documentation/quicktime-file-format/movie_header_atom), [matrix storage order](https://developer.apple.com/documentation/quicktime-file-format/movie_header_atom/matrix_structure), and [matrix scales](https://developer.apple.com/documentation/quicktime-file-format/matrices). Browser tests cover both versions, unknown versions, nontrivial signed/fractional matrices, exact matrix-field spans and byte-for-byte serialization.

### FBX node-name encoding decision

The currently exposed `first_node.name` is a byte-counted node identifier, retained as `char name[name_length]`. Blender's binary reader preserves this identifier directly as bytes in both its 13-byte (32-bit coordinates) and 25-byte (64-bit coordinates) node headers; it does not require UTF-8 decoding here. Switching this field to strict UTF-8 would reject byte sequences that the current inspection layout preserves. This decision does not claim that arbitrary identifier bytes form a valid semantic FBX document.

FBX string properties and embedded filenames are not exposed by the current schema. Their encoding and property-type framing must be established before adding typed property decoding; they must not inherit a node-identifier encoding rule. Browser tests verify the retained byte-code-unit behavior, embedded NUL, high bytes, exact spans and serialization for both header widths.

Primary implementation: [Blender FBX binary parser](https://github.com/blender/blender-addons/blob/main/io_scene_fbx/parse_fbx.py), specifically `read_fbx_elem_start32` and `read_fbx_elem_start64`.

### BMP calibrated color values

For V4/V5 DIB headers, calibrated RGB (`color_space == 0`) now uses a `fixed2_30[3][3]` endpoint matrix and `ufixed16_16` gamma channels. Other color spaces retain the 48 ignored calibration bytes instead of presenting them as meaningful values. This preserves storage size while demonstrating multidimensional fixed-point arrays and native conditions. Masks, image dimensions, offsets and profile identifiers keep their existing representations.

Sources: [Microsoft BITMAPV4HEADER](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/ns-wingdi-bitmapv4header) and [CIEXYZ](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/ns-wingdi-ciexyz). Browser fixtures cover both V4/V5 with signed fractional endpoints, three gamma values, inactive calibration fields, exact gamma spans and byte-for-byte serialization.

### Palm record identifiers

Palm/MOBI record-directory IDs now use `uint24> unique_id` rather than `uint8 unique_id[3]`. These are numeric big-endian 24-bit IDs, not text or UUIDs. The containing record remains eight bytes: offset (4), attributes (1), ID (3). The numeric type preserves zero for inspection even though valid records normally use nonzero IDs. Database-name text retains raw character code units; record content and compression remain outside this directory schema.

Source: [palm-pdb RecordId implementation documentation](https://jichu4n.github.io/palm-pdb/classes/RecordId.html). Browser tests verify two records, a non-symmetric ID, the maximum value, exact second-record ID span and byte-for-byte serialization.
